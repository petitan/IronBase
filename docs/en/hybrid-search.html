What is Hybrid Search?

Hybrid Search combines vector-based semantic search with keyword-based fulltext search using Reciprocal Rank Fusion (RRF). It delivers the best of both worlds: understanding the meaning of queries (semantic) while also matching exact keywords (fulltext).

🔀 RRF Fusion

Combines vector and fulltext rankings using Reciprocal Rank Fusion with configurable K and weights.

🧠 Auto-Embed

Automatically embeds queries server-side using FastText. No client-side embedding needed.

📊 Reranking

Multi-factor reranking: phrase match, keyword density, title boost, and short content penalty.

🌐 MMR Diversity

Maximal Marginal Relevance removes near-duplicates and ensures diverse results.

The hybrid_search tool is the unified entry point for all search operations. It supports two modes:

Mode When Description
Auto-embed vector parameter omitted Server embeds the query using the RAG collection's provider (FastText by default)
Explicit vector vector parameter provided Client provides a pre-computed embedding vector

Pipeline Overview

Every hybrid_search call goes through a 7-step pipeline:

│                          │                                            │

│                          │                                            │
│              ┌───────────┬───────────┐                          │
│              ▼                       ▼                          │

│            (HNSW cosine)                (TF-IDF ranked)              │

│              └───────────┴───────────┘                          │

│            score = Σ(weight_i / (K + rank_i))                        │
│                          │                                            │
│                          ▼                                            │
│  STEP 5    Reranking                                 [rerank=true]   │

Step Description Condition
1 Resolve vector/text field names; embed query if no explicit vector provided Always
1.5 Document-level AND: intersect posting lists to find docs containing ALL query terms match_scope="document" + mode="and"
2 Vector search via HNSW index (cosine similarity) Always
3 Fulltext search via TF-IDF index (keyword ranking) Always
4 RRF Fusion: combine vector and fulltext ranks with configurable weights Always
5 Reranking: apply phrase match, keyword density, title, and length boosts rerank=true (default)
5.5 Adjacent chunk merge: combine consecutive RAG chunks with overlapping text merge_chunks=true (default)
6 MMR diversity: penalize near-duplicate results using cosine similarity deduplicate=true (default)
7 Apply projection and build response Always

hybrid_search Tool Reference

hybrid_search — Unified Hybrid Search

Combines vector (semantic) and fulltext (keyword) search with RRF fusion, reranking, and MMR diversity filtering. Supports auto-embedding or explicit vector input.

Parameter Type Default Description
collection string — required Target collection name
query string — required Search query text
vector array[number] — optional Pre-computed embedding vector. If omitted, server auto-embeds the query
limit integer 10 optional Maximum number of results
text_field string auto optional Single text field for fulltext search
text_fields array[string] — optional Multiple text fields (best-field strategy). Overrides text_field
vector_field string auto optional Vector field name (auto-detected from RAG config)
mode string "or" optional Fulltext mode: "or" (any word) or "and" (all words required)
match_scope string "chunk" optional "chunk" = all words in one chunk, "document" = words across different chunks of the same document
search_mode string "balanced" optional Preset: "balanced", "semantic", or "keyword"
vector_weight number — optional Explicit vector weight (0.0–1.0). Overrides search_mode preset
fulltext_weight number — optional Explicit fulltext weight (0.0–1.0). Overrides search_mode preset
rrf_k number 20.0 optional RRF smoothing constant. Lower K = more spread between scores
title_field string — optional Field name for title-based reranking boost
rerank boolean true optional Apply reranking boosts (phrase, density, title, length)
deduplicate boolean true optional Apply MMR diversity reranking
mmr_lambda number 0.5 optional MMR balance: 1.0 = pure relevance, 0.0 = pure diversity
merge_chunks boolean true optional Merge adjacent RAG chunks with overlapping text
filter object — optional MongoDB-style query filter applied to results
projection object — optional Field projection ({"field": 1} include, {"field": 0} exclude)
provider string "fasttext" optional Embedding provider for auto-embed mode

Search Modes

Search mode presets provide LLM-friendly named configurations instead of raw numeric weights. Use search_mode to quickly choose a strategy:

Mode vector_weight fulltext_weight Best For
"balanced" 0.5 0.5 General-purpose search (default)
"semantic" 0.8 0.2 Conceptual questions, "what is...", topic exploration
"keyword" 0.2 0.8 Specific terms, names, product codes, exact phrases 
{
  "name": "hybrid_search",
  "arguments": {
    "collection": "knowledge_base",
    "query": "how does indexing work",
    "search_mode": "semantic"
  }
}

Custom Weights

For fine-grained control, set vector_weight and fulltext_weight explicitly. These override the search_mode preset.

Priority Order

Explicit vector_weight / fulltext_weight > search_mode preset > balanced default (0.5 / 0.5)

{
  "name": "hybrid_search",
  "arguments": {
    "collection": "articles",
    "query": "machine learning optimization",
    "vector_weight": 0.7,
    "fulltext_weight": 0.3
  }
}

Special cases:

Configuration Effect
vector_weight: 1.0, fulltext_weight: 0.0 Vector-only search (pure semantic)
vector_weight: 0.0, fulltext_weight: 1.0 Fulltext-only search (pure keyword)

Fulltext Options

mode: AND vs OR

The mode parameter controls how query terms are matched in the fulltext component:

Mode Behavior Example: query = "database indexing"
"or" (default) Match documents containing any query term Matches "database performance" or "indexing strategies"
"and" Match documents containing all query terms Only matches documents with both "database" AND "indexing" 
{
  "name": "hybrid_search",
  "arguments": {
    "collection": "docs",
    "query": "brake pad replacement cost",
    "mode": "and"
  }
}
AND mode + vector search

AND mode only affects the fulltext component. Vector search remains unfiltered, so RRF fusion can still return semantically relevant results even if they don't contain all keywords.

match_scope: Chunk vs Document

In RAG collections, documents are split into chunks. The match_scope parameter controls the granularity of AND matching:

Scope Behavior Use Case
"chunk" (default) All query terms must appear in the same chunk Short queries, precise matching
"document" Query terms can be spread across different chunks of the same document Long queries, multi-topic documents 
  Document "User Guide" (3 chunks)
  ┌─────────────────────┐┌─────────────────────┐┌─────────────────────┐
  │ Chunk 0              ││ Chunk 1              ││ Chunk 2              │
  │ "...brake pad..."    ││ "...replacement..."  ││ "...cost analysis..." │
  └─────────────────────┘└─────────────────────┘└─────────────────────┘

  Query: "brake pad cost"

  match_scope="chunk":     No chunk contains ALL three terms → 0 fulltext results
  match_scope="document":  "brake pad" in chunk 0, "cost" in chunk 2
                           → Document qualifies → all chunks searchable
        
{
  "name": "hybrid_search",
  "arguments": {
    "collection": "docs",
    "query": "brake pad replacement cost",
    "mode": "and",
    "match_scope": "document",
    "text_field": "content_text"
  }
}
Requirements

match_scope="document" requires mode="and" and a RAG collection (documents with doc_id field). Without these, it falls back to chunk-level matching.

Multi-field Fulltext Search

Search across multiple text fields simultaneously using text_fields. Each field must have a fulltext index. Results use a best-field strategy: the highest score from any field wins.

{
  "name": "hybrid_search",
  "arguments": {
    "collection": "articles",
    "query": "machine learning",
    "text_fields": ["content", "title", "abstract"]
  }
}
text_fields vs text_field

If both text_fields (array) and text_field (string) are provided, text_fields takes precedence. Each field in the array needs its own fulltext index (index_create_fulltext).

Reranking Pipeline

After RRF fusion produces an initial ranking, multiple reranking stages refine the results. Each stage is optional and can be toggled independently.

RRF Fusion (Step 4)

Reciprocal Rank Fusion combines rankings from different sources using a simple but effective formula:

  RRF Score = Σ ( weight_i / (K + rank_i) )

  Where:
    weight_i = source weight (vector_weight or fulltext_weight)
    K        = smoothing constant (default: 20)
    rank_i   = 1-based rank position in source results

  Example (K=20, balanced weights):
    Document appears at vector_rank=1, text_rank=5

    score = 0.5/(20+1) + 0.5/(20+5) = 0.02381 + 0.02000 = 0.04381

The rrf_k parameter controls score spread. Lower K values create more separation between high-ranked and low-ranked results:

K Value Score Spread (top-10) Effect
60 0.00049 Very compressed — reranking has minimal effect
20 (default) 0.00430 8.8x wider spread — reranking is meaningful
20 + title_field 0.01162 23.7x wider — title boost amplifies differences

Reranking Boosts (Step 5)

When rerank=true (default), four multiplicative boost factors are applied to each result's RRF score:

Factor Boost Condition
Exact phrase match 1.5x The exact query string appears in the document text
Keyword density 1.0x – 1.3x Proportion of query terms found in the document (scaled linearly)
Title match 1.0x – 1.5x Query terms found in the title_field (requires title_field parameter)
Short content penalty 0.8x Document text is shorter than 50 characters

The final score is: _final_score = _rrf_score * phrase_boost * density_boost * title_boost * length_factor

Title Boost

To enable title-based boosting, set title_field to the name of the field containing document titles (e.g. "title"). Without this parameter, title boost is always 1.0x (no effect).

Adjacent Chunk Merge (Step 5.5)

RAG chunking with overlap (~100 chars) causes adjacent chunks to duplicate boundary text. When both chunks appear in the top results, they waste slots with redundant content.

When merge_chunks=true (default), consecutive chunks from the same document are merged:

Aspect Detail
Trigger Same doc_id + consecutive chunk_index values
Text merge Overlap removed using start_char/end_char boundaries (UTF-8 safe)
Score max(_final_score) from the merged run
Embedding Embedding from the highest-scoring chunk in the run
Metadata chunk_merged: true, chunks_in_merge: N, updated start_char/end_char
Position After reranking, before MMR — merged chunks feed into diversity filtering

MMR Diversity (Step 6)

Maximal Marginal Relevance (MMR) reduces near-duplicate results by penalizing documents that are too similar to already-selected results.

  MMR(c) = λ * relevance(c) - (1 - λ) * max_similarity(c, selected)

  Where:
    λ (mmr_lambda)       = balance between relevance and diversity
    relevance(c)         = normalized _final_score
    max_similarity(...)  = highest cosine similarity to any already-selected result
mmr_lambda Behavior
1.0 Pure relevance (no diversity penalty) — equivalent to deduplicate=false
0.5 (default) Balanced: equal weight to relevance and diversity
0.0 Maximum diversity: aggressively penalizes similar results
Embedding required

MMR uses cosine similarity between document embeddings. Results without embeddings are ranked by relevance only (no diversity penalty applied).

Basic Search (Auto-embed)

The simplest form: just provide a collection and query. The server auto-embeds the query and uses balanced weights.

{

  "arguments": {
    "collection": "knowledge_base",
    "query": "how to create indexes"
  }

Best Practices

Performance Tips

• Use projection to return only needed fields — reduces response size
• Set an appropriate limit — higher limits increase RRF computation
• search_mode presets are zero-cost — prefer them over manual weight tuning
• title_field adds minimal overhead but significantly improves relevance
• merge_chunks=true (default) reduces redundant results in RAG collections

When to Use What

AND vs OR Mode

Scenario Recommended Mode Why
Short queries (1–2 words) "or" (default) AND is equivalent to OR for single-word queries
Broad exploration "or" Cast a wide net, let reranking sort by relevance
Multi-term specific queries "and" Ensures all concepts are present in results
Product/entity search "and" All terms are typically required (e.g. "brake pad ABS")

Chunk vs Document Scope

Scenario Recommended Scope Why
Short documents (single chunk) "chunk" (default) Document scope has no effect on single-chunk documents
Precise passage retrieval "chunk" Finds the exact chunk containing all terms
Long documents, multi-topic queries "document" Terms may be spread across different sections
QA over technical manuals "document" Answer may require context from multiple sections

Search Mode Selection

Query Type Recommended Mode Example
Conceptual / "What is..." "semantic" "how does garbage collection work"
Exact terms / product codes "keyword" "ABS-2024-XR brake assembly"
General / mixed "balanced" (default) "indexing performance optimization"
Heavy Queries

Combining match_scope="document" + mode="and" + text_fields (multi-field) + high limit is the most expensive configuration. For large collections (100K+ chunks), consider narrowing the query or using filter to reduce the search space.
